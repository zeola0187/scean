# 情境驗證、精簡與交付

## 1. 先驗證人物，而不是替人物預演劇本

完成人物草稿後，至少從不同性質的情境檢視人物。可選平常互動、價值衝突、突發壓力、重要他人提出要求等；目的在於測試其判斷依據是否足以產生合理而不只有單一答案的反應。多角色卡可以加入一項角色間互動測試。

情境推演是**測試資料**：

- 可用簡短、具體的例子讓製卡者理解人物可能如何演繹。
- 不把測試中的事件當作已發生的角色過往。
- 不把測試得到的特定行動當成未來必然反應。
- 不自動寫入世界書或描述欄；若測試暴露出人格理由不充分，應回頭改善抽象的判斷機制，而不是複製測試故事。
- 不宣稱某個測試結果能保證不同模型或 Preset 都會產生一致行為。

對話中可視情況展示一兩個有啟發性的短例，無需把每項內部分析清單公開。若製卡者只要看成果，重點放在新的角色設計及可觀察差異。

## 2. 精簡成可使用的人物種子

將完整的創作分析整理為 RP 模型需要的資訊：

- 他是一個怎樣的人，通常根據什麼原則作決定。
- 什麼重要經歷、關係、社會處境或心理落差支持上述判斷。
- 哪些態度可能受情境、身份或時間改變；哪些只是當前狀態。
- 如果有意義，說明角色為何把自己的行為理解成另一回事。

刪除重複的形容詞、只是換句話說的行為例子、內部審查標記、為了填滿格式而設計的細節，以及情境驗證用的劇情。精簡不是刪去必要的人格動因；資訊足夠、可推演，比字數越少越好更重要。

不強制所有角色有相同欄位、特質數量、完整人生背景、固定 Token 額度或同一種寫法。製卡者若想保留更完整的個人史，尊重該次要求。

## 3. 決定資料放在哪裡

資料編排屬於製卡技巧，而非人格設計本身。依照卡片規模、角色數量、世界書條件與宿主功能選擇：

- 常態需要的人格依據，可放在可穩定取得的資料位置。
- 只在特定人物、場所或事件有關時才需要的細節，可考慮選擇性取得。
- 需要長期追蹤的狀態，可以視需求使用持久化變數；變數不能取代狀態更新與注入的可靠性檢查。
- 拆開儲存不必然減損精度；漏注入、互相矛盾或失去關鍵脈絡才可能影響演繹品質。

應在實際宿主中驗證：本輪哪些資料被送進模型、是否受 Token 預算與掃描規則影響。不能單憑 Skill 描述，就假定世界書每條都能被正確觸發。不修改不熟悉的 runtime，不為了裝載 Skill 改寫宿主運作邏輯。

## 4. 寫入與回報

只有在使用者授權後才寫入；碰到與已確認事實的直接衝突，先取得抉擇。工作副本與版本保護遵守宿主現有機制，不覆蓋原始素材、不破壞未知欄位。

回覆製卡者時，優先提供：

1. 本輪塑造或修正了什麼人物特質／心理依據。
2. 有哪些值得注意的新關係、緊張點或可能的發展條件。
3. 若需要，給一至兩個**明確標為假設**的情境短例（不屬於卡片內容）。
4. 只有真正阻擋繼續工作的素材衝突、尚未完成寫入或匯出，才額外要求使用者決定。

## 5. 快速品質檢查

- [ ] 是否有足夠的人格依據，讓 RP 模型能在未預先列出的情境下自行推演？
- [ ] 是否不必要地「洗白」、中和或弱化了極端人物？
- [ ] 有沒有把世界制度缺口自行補成已確定設定？
- [ ] 有沒有把人物與玩家必然綁定，或預先安排不可逆的關係結局？
- [ ] 有沒有把驗證情境的行動寫進角色設定？
- [ ] 是否保留重要心理脈絡，同時剔除重複與制式填充？
- [ ] 變更是否只落在已授權範圍？需要的來源與技能分工是否清楚？
