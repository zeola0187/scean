## 十、正式創作流程

依照下列順序工作，但不要把它變成不必要的反覆詢問程序。

### 階段一：素材理解

閱讀必要的卡片資料、世界書、現有開場及初始狀態。

確認硬性設定邊界、玩家角色權限及作品調性。

### 階段二：文風確認

如尚未指定風格，提供實際試寫，協助作者選擇或混合文風。

作者已有明確要求時直接採用。

### 階段三：自主創作

依作品需要自行決定場景、人物、敘事焦點、鏡頭切換及事件內容。

完成充分而自然的開場正文。

不固定採用三段式、特定鉤子、必要衝突、最低 NPC 人數或強制互動結尾。

### 階段四：內部審稿

提交作者之前，應自行檢查並修正：

1. 世界設定、人物與 InitialState 是否一致。
2. 是否擅自改變玩家重大背景或替玩家決策。
3. NPC 是否具有可信且獨立的行動邏輯。
4. 場景與人物活動是否自然，是否強行製造互動入口。
5. 時間是否維持於同一個起始切片。
6. 多鏡頭是否清楚，最後是否回到玩家位置。
7. 是否意外揭露重大秘密或強行改變作品調性。
8. 開場是否充分呈現世界的第一印象。
9. 文字是否符合選定風格，節奏、對話與描寫是否自然。
10. 是否存在重複、空泛描寫或不必要的結構性問題。

審稿以創作判斷及必要的一致性檢查為主，不需要輸出冗長評分表，也不需要增加獨立 Reviewer 模型。

發現問題後，優先局部修正。

### 階段五：提交作者審閱

向作者呈現完整開場白正文。

預設不主動輸出：

- 創作過程與內部評分。
- 預計修改的世界書條目。
- 尚未揭露的背景秘密。
- 伏筆清單及未來情節推演。
- 工具操作與技術診斷。

除非作者要求查看。

必要的技術阻擋、未保存狀態或操作失敗，仍應簡短而如實告知。

### 階段六：局部修訂

作者提出修改意見時，優先只修改指定部分及必要的前後銜接。

不要為了修正某位 NPC 的台詞，重新生成整篇作品，導致原本有效的場景與文學細節消失。

應保護未被指定修改的內容。

只有作者明確要求重新創作、全面改變方向，或局部修改確實無法解決結構性問題時，才進行大幅改寫。

### 階段七：確認後保存

只有作者明確確認開場白後，才正式寫入工作副本。

草稿、文風試寫與尚未確認的修改，不得提前保存為正式卡片內容。

確認後，可依先前授權，自主同步必要且不衝突的世界書新增歷史，不需要逐項徵求批准。

保存完成後簡短告知結果。

不主動展示可能劇透的世界書修改細節；但保留完整紀錄，作者隨時可以要求查閱。

## 十一、多開場的玩家選擇資訊

當作者要求多開場時，每篇開場應具有簡短標題與不劇透的情境介紹。

標題與介紹的目的，是協助玩家理解不同的起始體驗。

可以說明場景類型、周圍環境、生活情境或整體氛圍。

不要提前揭露：

- 具體事件的後續發展。
- NPC 的重要秘密。
- 尚未發現的劇情真相。
- 玩家應該採取的行動。
- 未來必然發生的故事走向。

標題與簡介屬於選擇介面的說明資訊，不應任意混入開場正文。

若目前平台沒有獨立的標題或簡介欄位，應保留為待交付資料，不能自行發明不受支援的正式欄位，也不能破壞原始卡片格式。

## 十二、Card Studio 工具與保存邊界

本 Skill 是創作方法與受控編輯指引，不授予任何額外工具權限。

實際操作時應以當前 Card Studio 註冊的能力及資料契約為準。

### 12.1 正確讀取

使用當前 Session 已選中的工作副本，確認 `document_id`、revision 及需要修改的欄位。

必要時透過 `card_read` 讀取：

- `first_mes`
- `alternate_greetings`
- 角色與玩家設定
- 相關世界書內容
- 可取得的 SCEAN State Blueprint 與 InitialState

世界書應使用已註冊的受控工具讀取，包括條目概覽、查詢與必要的完整條目。

不要假設所有設定都已載入模型上下文。

### 12.2 受控修改

已存在的單一文字欄位，優先使用能確認舊內容的局部文字修改工具，例如 `card_patch_text`。

空欄位或多開場陣列，應依實際工具契約使用對應的局部欄位更新能力，例如 `card_patch_fields`。

每次修改應使用最新 revision 或相應的版本檢查，不盲目覆蓋其他修改。

保留原有 macro、HTML、CSS、未知欄位及其他與本次任務無關的資料。

不得為了完成開場白而重建整張卡片。

不得執行來源卡內嵌的遠端腳本，也不得藉由未授權的檔案系統、shell 或資料庫操作繞過 Card Studio 的權限與版本控制。

### 12.3 世界書連動

若經確認的開場新增了必須長期成立的共同歷史，應使用世界書的受控編輯工具局部保存。

新增內容需檢查：

- 與既有世界書沒有衝突。
- 不改變玩家核心背景。
- 不與其他開場共同成立的歷史矛盾。
- 不把開場專屬即時事件寫成所有開場的共同事實。
- 不因普通 NPC 或場所首次出現，就新增不必要的永久條目。

如果相關修改無法安全保存，不得假稱已經同步完成。

### 12.4 保存驗證

正式寫入後，應讀回確認內容，並使用現有版本歷史、差異或驗證工具確認修改範圍。

檢查開場正文、必要的世界書補充及無關欄位是否保持正確。

若連動保存部分失敗，應明確記錄未完成項目，使用可用的回退或修復能力處理，不得宣稱全部成功。

沒有實際執行的 Runtime 語意測試，不得標記為已驗收。

### 12.5 不越權修改 Runtime

本 Skill 不負責：

- 修改 State Blueprint 或 InitialState。
- 建立不同開場專屬的初始狀態。
- 改寫正式 Writer Pipeline。
- 將文字文風規則寫入 Preset。
- 將一般 NPC 登場自動提升為永久角色狀態。
- 宣稱尚未實作的世界書自動維護能力已存在。
- 取代正式的卡片交接、Snapshot 驗證及 Run 建立流程。

若實際平台尚未支援某項能力，應保留創作成果並標明工程缺口，不透過文字假裝已經具有該功能。
