# timecal.3 局部時間修補與驗收

基準為正式 `1.6.2-local.w29.2d.rc3.1.timecal.2`；此候選未包含 Natural Runtime A/B 架構。本次只作離線／mock 驗證，不以真模型測試。

- `resolve_turn_time` 的 `advance_to.target` 必須恰好包含一個日期 selector。同日用 `dayOffset:0`；不能只填時段，也不會自動改成翌日。
- 明確列入白名單、尚無副作用的時間 selector／唯讀歷史查詢參數錯誤，會回傳安全 code、欄位、原因、候選未變更。每 attempt 最多一次修正，仍使用既有 5 輪 Director／6 次工具上限。Director 規劃階段共用固定期限與最多 10 次實際派送上限（5 輪、每輪既有技術重試最多 2 次），不因修正更新期限或預算；實際派送逐次記帳。
- 已成功的工具結果保留，修正時相同且來源相符的成功工具只讀回結果，不重執。失敗批次後續工具明確標示未執行。未解決的工具錯誤不能直接略過進入 Writer。
- `NEEDS_TIME_PRECISION` 不作自動猜測。舞臺的「補充／確認時間」讓玩家輸入故事日序、時段或時刻，勾選確認後，與下一次輸入一起提出。這份表單本身不修改存檔。
- 權威時間範圍內的明確細化，使用與 Run／Snapshot／version／head／Clock hash 綁定的玩家確認。Host 只作結構及區間驗證；不解析正文、不用關鍵字猜時刻、不修改既有 baseline 或歷史。來源變更會清除表單確認並拒絕過期提案。
- 初始時間只有日精度時有提示，讓作者／玩家明確確認。開場寫出某時刻不會自動更新權威 Clock。
- 權限、跨 Run、持久化、取消、期限、派送預算與結果未知仍安全停止；提交結果未知先核對 canonical receipt，不重跑已提交回合。

## 同一場如何使用（安裝完成後）

開啟原有演出，保留原輸入，點「補充／確認時間」。如果你確認場景應是目前已知時間範圍內的某個時段，選「確認目前時間」，填寫故事第幾日與時段／時刻，確認後再送出。若你的意思是明確前進到較晚時間，選「推進至」。

例如，只有當玩家本人確認是第 1 日下午，才選第 1 日及「下午」；程式不會預填或代替玩家認定這個值。成功時，正文、State、Clock、活動與 receipt 同一筆原子提交；失敗時保留既有正式回合。若收到時間澄清，請使用表單補足，而非持續按一般重試。

沒有選時間確認時維持既有流程；安裝不會直接校正任何既有 Run。

## 存檔與還原

未使用玩家時間確認的舊 Run 沿用既有 v9／v10 存檔。使用確認後，匯出格式為 v11，明示 `storyTime.playerConfirmation.v1` 能力；舊版不能當作相容格式讀取，避免誤解或丟失確認來源。

還原軟體之前，先正常停止服務並保存升級後的新資料。若尚未進行新回合，可在完整還原點核對下重裝原 timecal.2；若已產生 v11 回合，不可盲目降版或用舊備份覆蓋新進度。應先保留所有新 Run、證據與設定，再另行制定與確認還原方案。

安裝前必須確認前景／背景工作已安全收束、來源無漂移、完整備份可還原。無法確認退出或提交結果時停止安裝；不強殺程序、不改安全權限。
