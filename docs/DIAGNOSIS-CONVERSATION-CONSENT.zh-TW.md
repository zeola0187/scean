# 診斷回修的聊天同意

診斷讀取與編輯同意仍分開。Agent 先用 `prepare_edit` 記錄要改的方向與確切工作卡版本，再於正常回覆中完成討論。使用者在同一對話明確同意後，現有欄位編輯與 Blueprint／面板保存共用的閘門會核對 Host 訊息；不必輸入固定句型，也不必另找編輯器按鈕。

例如「確認修改，只改測試欄位」、「同意這個修改」及「好，幫我改，但不要改性格」可在正確提案後作為同意。這些只是例子，不是密語。問句、假設、引用、拒絕及暫緩不會放行；不確定時仍需要玩家在正常聊天澄清。

## Host 核對

- 僅接受目前 Session 的真正 `user/message`，來源必須是既有 owner RPC。模型文字、工具回覆、`ask_user_question` 的結果、故事或 Snapshot 文字不能代替它。
- 同意必須晚於該提案及其可見討論，並綁定診斷、修正方向、目標種類、卡片身份及保存版本。提案指紋防止方向或對象改變後沿用同意。
- 重複準備完全相同的提案不會清掉已討論的提案；方向、目標或版本不同則必須重新討論及取得新同意。舊訊息不能回頭批准新提案。
- 保存仍使用 `expected_revision`，並在交易提交前重新檢查；撤銷、Session 失效、新的使用者撤回及版本衝突仍阻擋寫入。歷史讀取失敗會停止聊天授權，不假裝看到了使用者同意。
- 保留使用者明示不改性格、世界書或開場的既有欄位保護。Host 比對的是提案身份、方向文字與版本，不宣稱能判斷所有故事規則的自然語意；Agent 仍需遵循已同意方向與限制。

`DIAG_EDIT_CONSENT` 現在回傳細分 `reason` 與正常聊天的下一步。它不代表使用者權限不是完整模式，也不代表必須改在編輯器確認。沒有診斷的正常製卡流程不受影響。

維持目前 Session 生命週期政策，沒有加入新的隱藏時間限制、持續權限或模型呼叫。本地修復完成不代表已安裝或推送；部署狀態由獨立交付回執記錄。
